# Matthew Way Studio pilot: quick guide

This is the side-by-side Pi GUI v1.0.1 Matthew Way Studio build installed at `%LOCALAPPDATA%\Programs\PiGuiMatthewWayStudio`. The earlier Pi GUI and OpenCode installations remain in place. Start `pi-gui.exe` in that folder. This portable build uses Pi's normal user profile unless launched with a separate profile for a disposable test.

## Choose a role

Use Pi's slash-command menu in the thread composer: choose a role prompt (for example, `/role-review`) and send it with the task. The six Matthew Way role presets are `/role-plan`, `/role-build`, `/role-fast-worker`, `/role-researcher`, `/role-review`, and `/role-release-engineer`; they shape the task prompt and do not change the thread's model. To invoke a skill, open Skills, search for the skill, select it, choose Try, then send a request that uses it; Try alone only fills the composer. The eight installed Matthew Way skills are `agent-packet`, `bounded-context`, `consequence-check`, `independent-inspector`, `intent-to-plan`, `research-second-opinion`, `reuse-first`, and `semantic-boundary-review`.

## Switch models

Use the GUI model picker in the current thread. That changes the thread model, independently of the role prompt. `/studio models` lets you save an authenticated model and a supported thinking level for each Studio role. These preferences apply to future workers only and do not change the current thread. The version-2 preferences retain compatibility with existing version-1 route settings. Check the provider and model shown in Pi before sending.

## Use Studio safely

1. Open the Studio view and create a draft, or begin in a project thread.
2. `Prepare in current thread` prefills the `/studio` packet and returns to the thread. It does not send anything.
3. Choose the thread model, review the packet, then send it. `/studio` starts with an observed plan; it may inspect and propose, but does not dispatch workers or change files.
4. Read the plan. Return to Studio, select the same prepared thread, then choose **Start in prepared thread** to send `/studio start` and record the run as running. If submission fails, the run remains in its prior state. Recheck the plan if the repository or assumptions have changed.

Starting an observed run now sends `/studio start` to the exact thread that received its planning packet before marking the ledger running. A desktop restart changes persisted running plans to paused and records a recovery note before any new dispatch can happen. Select the coordinator and choose **Resume after reconciliation** only after checking its session and worker threads, repository status, verification results, and GitHub checkpoints; existing running or completed milestones must not be duplicated. Pause also records a durable gate that blocks new Studio child-worker creation and coordinator follow-ups; work already in flight may continue. Resume reissues `/studio start` in the prepared coordinator thread so it can reconcile current state. Stop records a terminal state, selects the coordinator, and invokes Pi's native cancel-current-run path for the coordinator and its app-owned children. An Electron runtime test now proves Stop aborts a real Pi child session's in-flight request to a local stalled model fixture; cancellation against external provider endpoints has not been tested. Use Live correction to save Matthew's correction through its dedicated UI-authorized path and prepare a packet in the same coordinator thread; it is not sent automatically. The record lists currently unfinished milestone IDs. The coordinator must preserve correction history, reconcile affected work, and include a concise summary before marking the correction applied. Existing milestone IDs, instructions, and dependencies remain immutable; plan changes cancel affected old milestones through their lifecycle and append replacement milestones with new IDs. This is guided reconciliation, not a guarantee that the coordinator completes every step. GitHub pull requests can be refreshed manually from the saved PR link; Pi uses the signed-in `gh` client for a read-only API lookup, and records merged only when the response includes merge commit evidence. Refresh is not automatic, and Pi never merges or publishes on its own. This is not yet an automatic completion auditor. Pi native child-thread orchestration is available to the `/studio` workflow, but the complete continuous milestone and independent audit pipeline is not yet commissioned. Nothing deploys or authorizes metered inference automatically.

The coordinator's current verification guidance limits active child workers to two, separates the implementation worker from an `independent-inspector` child, and requires repository-diff and test evidence before it records PASS. Every Studio worker dispatch now needs a stable task ID; repeating the same task ID returns the existing child instead of starting duplicate work. Pi blocks a new transition to milestone complete unless the linked inspector thread is complete, its final message starts with PASS, its runtime record includes successful Git diff/status inspection and a test/check command, and the coordinator has read its output. FAIL permits at most two bounded repair attempts; INCONCLUSIVE must remain unaccepted. The gate verifies those runtime signals, but it cannot determine whether the inspector's reasoning or chosen check was correct; read the inspector's actual thread and tool evidence before relying on its report.

Delivery policy is host-owned per run. Recording a plan in the Studio view offers a **Delivery** choice: `GitHub pull request (default)` keeps dependent milestones gated on an observed GitHub merge, while `Local-only demonstration` is the authorised route for disposable local projects where dependent milestones unlock on internally verified local completion. The choice is stamped once at run creation through the UI-authorised save path and is immutable afterwards; milestones appended later inherit it. The model-facing `save_studio_run` tool cannot select, introduce, or change the policy — a model-claimed `local` policy or requirement is always overridden to `github-pr` — and the coordinator binding (`coordinatorSessionId`) survives every model save because the host preserves it. Cancelling a milestone (for example the draft placeholder a coordinator replaces with its real plan) no longer prevents a finished run from reaching `completed`.

## Execution economy

Studio runs on host-owned waiting and compact receipts so coordination costs as little inference as possible:

- **Host-side evidence reconciliation.** Verification evidence is derived from live transcripts, and a concurrent child's event stream can delay the coordinator's own `read_thread` result reaching the projection. Completion saves now wait inside the host (bounded, 90 s default, `PI_APP_STUDIO_EVIDENCE_WAIT_MS` overrides, 0 disables) for the derivation to settle instead of rejecting and making the model re-save. No verification requirement is weakened: the gate still rejects when evidence never arrives, and structural gaps (no linked inspector, missing coordinator binding) still reject immediately without waiting. A post-wait revision guard prevents clobbering a save that landed during the wait.
- **Compact worker/inspector receipts.** `read_thread` returns a receipt — status, message counts, and the last five messages truncated to 240 characters — instead of dumping up to 60 full messages into the coordinator context. The complete transcript and all evidence stay host-side; `read_thread` with `full: true` returns the full bounded transcript (50 KB cap) on demand.
- **Idle coordination costs zero inference.** `wait_for_child_threads` now accepts timeouts up to 600 s per call, so the coordinator blocks host-side through long worker runs instead of re-issuing short waits; the two-child concurrency cap and supervision loops are unchanged.
- **Combined accounting.** The demo lane writes `cost-report.json`: model turns per actor, tool calls by name, save acceptance/rejection counts, elapsed time, coordinator context growth, and combined per-session usage from Pi's own accounting (context tokens, input/output/cache totals where the provider reports them).

Measured on the identical three-milestone demo (same spec, same machine; baseline run `studio-86466a8d`, economy run `studio-cf0506c7`): `save_studio_run` calls 155 → 13, rejected saves 143 → 1 (the remaining one is the intentional dependency-gate probe), evidence-lag rejections 142 → 0, coordinator tool calls 178 → 36, elapsed ~204 s → ~49 s, and the coordinator's final context was ≈9.2k estimated tokens across 74 messages. Fixture token totals read zero because the scripted provider emits no `usage`; context-token counts are Pi's real numbers, and real-model runs report true token totals.

Pattern credits (ideas adapted, no code copied; all MIT-licensed pi extensions): `earendil-works/pi`'s subagent example (bounded model-visible output with full detail retained host-side, per-agent usage lines), `tintinweb/pi-subagents` (completion notification previews with full results on demand, graceful turn limits, visible per-agent accounting), `fitchmultz/pi-subagents` (end the turn for completion delivery instead of polling; concise inspect summaries with `full: true` detail), and `n-r-w/pi-agent-suite` (host-side `subagent_wait`, context projection keeping stale tool output out of the model context, combined `/usage` accounting with cache statistics).
