# Matthew Way Studio pilot: quick guide

This is the side-by-side Pi GUI v1.0.1 Matthew Way Studio build installed at `%LOCALAPPDATA%\Programs\PiGuiMatthewWayStudio`. The earlier Pi GUI and OpenCode installations remain in place. Start `pi-gui.exe` in that folder. This portable build uses Pi's normal user profile unless launched with a separate profile for a disposable test.

## Choose a role

Use Pi's slash-command menu in the thread composer: choose a role prompt (for example, `/role-review`) and send it with the task. The six Matthew Way role presets are `/role-plan`, `/role-build`, `/role-fast-worker`, `/role-researcher`, `/role-review`, and `/role-release-engineer`; they shape the task prompt and do not change the thread's model. To invoke a skill, open Skills, search for the skill, select it, choose Try, then send a request that uses it; Try alone only fills the composer. The eight installed Matthew Way skills are `agent-packet`, `bounded-context`, `consequence-check`, `independent-inspector`, `intent-to-plan`, `research-second-opinion`, `reuse-first`, and `semantic-boundary-review`.

## Switch models

Use the GUI model picker in the current thread. That changes the thread model, independently of the role prompt. `/studio models` opens the Studio role-preference selector; a saved preference affects future Studio task plans only, not the current thread model. Check the provider and model shown in Pi before sending.

## Use Studio safely

1. Open the Studio view and create a draft, or begin in a project thread.
2. `Prepare in current thread` prefills the `/studio` packet and returns to the thread. It does not send anything.
3. Choose the thread model, review the packet, then send it. `/studio` starts with an observed plan; it may inspect and propose, but does not dispatch workers or change files.
4. Read the plan. Return to Studio, select the same prepared thread, then choose **Start in prepared thread** to send `/studio start` and record the run as running. If submission fails, the run remains in its prior state. Recheck the plan if the repository or assumptions have changed.

Starting an observed run now sends `/studio start` to the exact thread that received its planning packet before marking the ledger running. A desktop restart changes persisted running plans to paused and records a recovery note before any new dispatch can happen. Select the coordinator and choose **Resume after reconciliation** only after checking its session and worker threads, repository status, verification results, and GitHub checkpoints; existing running or completed milestones must not be duplicated. Pause also records a durable gate that blocks new Studio child-worker creation and coordinator follow-ups; work already in flight may continue. Resume reissues `/studio start` in the prepared coordinator thread so it can reconcile current state. Stop records a terminal state, selects the coordinator, and invokes Pi's native cancel-current-run path for the coordinator and its app-owned children. Active-worker cancellation has not yet been proven in a live run. Use Live correction to save Matthew's correction through its dedicated UI-authorized path and prepare a packet in the same coordinator thread; it is not sent automatically. The record lists currently unfinished milestone IDs. The coordinator must preserve correction history, reconcile affected work, and include a concise summary before marking the correction applied. Existing milestone IDs, instructions, and dependencies remain immutable; plan changes cancel affected old milestones through their lifecycle and append replacement milestones with new IDs. This is guided reconciliation, not a guarantee that the coordinator completes every step. GitHub pull requests can be refreshed manually from the saved PR link; Pi uses the signed-in `gh` client for a read-only API lookup, and records merged only when the response includes merge commit evidence. Refresh is not automatic, and Pi never merges or publishes on its own. This is not yet an automatic completion auditor. Pi native child-thread orchestration is available to the `/studio` workflow, but the complete continuous milestone and independent audit pipeline is not yet commissioned. Nothing deploys or authorizes metered inference automatically.

The coordinator's current verification guidance limits active child workers to two, separates the implementation worker from an `independent-inspector` child, and requires repository-diff and test evidence before it records PASS. Every Studio worker dispatch now needs a stable task ID; repeating the same task ID returns the existing child instead of starting duplicate work. Pi blocks a new transition to milestone complete unless the linked inspector thread is complete, its final message starts with PASS, its runtime record includes successful Git diff/status inspection and a test/check command, and the coordinator has read its output. FAIL permits at most two bounded repair attempts; INCONCLUSIVE must remain unaccepted. The gate verifies those runtime signals, but it cannot determine whether the inspector's reasoning or chosen check was correct; read the inspector's actual thread and tool evidence before relying on its report.

Delivery policy is host-owned per run. Recording a plan in the Studio view offers a **Delivery** choice: `GitHub pull request (default)` keeps dependent milestones gated on an observed GitHub merge, while `Local-only demonstration` is the authorised route for disposable local projects where dependent milestones unlock on internally verified local completion. The choice is stamped once at run creation through the UI-authorised save path and is immutable afterwards; milestones appended later inherit it. The model-facing `save_studio_run` tool cannot select, introduce, or change the policy — a model-claimed `local` policy or requirement is always overridden to `github-pr` — and the coordinator binding (`coordinatorSessionId`) survives every model save because the host preserves it. Cancelling a milestone (for example the draft placeholder a coordinator replaces with its real plan) no longer prevents a finished run from reaching `completed`.
